# Streakly: architecture

| Choice | Decision | Why |
|---|---|---|
| Parts | One part, `app`: an Expo 58 app (React Native 0.88, expo-router, TypeScript), built as is for the phone and exported to the web with `expo export --platform web`. On the web, `scripts/serve.mjs` serves it on port 3000 with cross-origin isolation, which SQLite's web build needs. The work falls into `src/app` (screens), `src/lib` (data, days, streaks, saving), `src/components` and `src/theme`. This is the Expo template, not `next-app`, because the repo is built that way. | The spec makes Streakly "a real phone app" that "also runs in a browser up to 1440 px", and AXB AIOS decided the app kind is Expo, as the repo is built. |
| Pages | expo-router file routes, all drawn on the device; nothing is server-rendered. `src/app/_layout.tsx` is a Stack that opens the database before the first screen. `(tabs)/_layout.tsx` holds Today `/` (`index.tsx`), Week `/week` and Settings `/settings`, and redirects to the guide `/welcome` while `guideDone` is false. Add habit is `/habits/new` and Edit habit is `/habits/[id]`. `today.tsx` and `+not-found.tsx` redirect to `/`. Content sits in one centred column (`tokens.size.content`). No new route: the "Archived habits" section sits inside `/settings`, and Edit habit gets "Archive habit" above "Delete habit". On `/welcome`, card 3 shows only "Get started". | Screens guide, today, week, add-habit, edit-habit and theme. routes: "/today" and any unknown address go to Today. archived-list puts the section "in Settings", archive.button puts "Archive habit" "above the 'Delete habit' button", and guide-last-card asks for "only a 'Get started' button". |
| API | None: there's no server, there are no HTTP routes and there's no `contract/openapi.yaml`. Screens call `src/lib/store.ts` directly: `loadList`, `loadHabit`, `loadArchived`, `loadSettings`, `addHabit`, `updateHabit`, `archiveHabit`, `restoreHabit`, `deleteHabit`, `toggleTick`, `setTick`, `saveTick`, `failedTick`, `reorder`, `setTheme`, `setGuideDone` and `deleteAll`. Each one throws on failure: a `RangeError` with the spec's text for a refusal, or `TickNotSaved` (which carries the change) for a tick that didn't save. | Data and risk: "nothing is uploaded, nothing is shared and nothing updates live from elsewhere". |
| Data | SQLite on the device through `expo-sqlite` (`app.db`, `journal_mode=DELETE`, `synchronous=FULL`), opened in `src/lib/db.ts`. One queue serialises every query and every whole transaction. The tables are `habits(id, name, colour 0–7, position, created_on, archived_at, restore_place)`, `ticks(habit_id, date 'YYYY-MM-DD', PK(habit_id, date))` and `kv(key, value)`, which holds `theme`, `guideDone` and `failedTick`. They're made by the append-only `steps` in `db.ts` (`schema_version`). Step 2 is `ALTER TABLE habits ADD COLUMN archived_at INTEGER` (null means not archived) and `ADD COLUMN restore_place INTEGER`. There are no uploads and no live events. | Data and risk now lists, for habits, "whether archived, when archived and the place to restore to", and archived habits keep their ticks. |
| Archive | `archiveHabit(id)` takes only the id, so it archives the habit as stored and never sees unsaved form edits. It runs as one transaction. It sets `restore_place` to the habit's 0-based index among the habits that aren't archived. It sets `archived_at` to `max(Date.now(), MAX(archived_at) + 1)`, so later archives always sort later. It deletes `kv.failedTick` if that change is on this habit, and leaves the ticks alone. There's no confirm prompt; once the save succeeds, the screen goes to `/`. On failure, Edit habit keeps its form state and shows "Couldn't save. Try again.". | archive: "at once, with no confirm prompt, as it was last saved", "stores the habit's place", "clears its remembered failed tick change". form-save-error.archive: stay on the form when the save fails. archived-list: "most recently archived first". |
| Restore | `restoreHabit(id)` runs as one transaction. It reads the non-archived ids in order and inserts this one at `min(restore_place, count)`. It rewrites `position` 0…n for that list and clears `archived_at` and `restore_place`. Ticks aren't touched. It runs through `use-save` in Settings, so a failure shows "Couldn't save your change" with "Try again" and the habit stays listed. | restore: "back at its stored place … or at the end of the list if there are now fewer habits than that place". restore.place-fewer gives "Read", "Walk". save-error.restore. |
| Lists | `loadList` returns only habits with `archived_at IS NULL`, so Today's rows and its "<ticked> of <total> ticked" summary, Week's rows and the "No habits yet" state all leave archived habits out. `loadArchived` returns the archived habits `ORDER BY archived_at DESC` with their ticks, so Settings can show "Best: <n>". The Settings section wraps it in `testable("/settings/archived", …)` and has its own "Loading archived habits…", "Couldn't load archived habits" + "Try again" and "No archived habits" states. Archived rows have no delete control. `loadHabit` returns `archivedAt`, and Edit habit shows "This habit isn't here any more." for a habit that is archived as well as for one that is missing. `findHabit`, used by the test hooks, still finds archived habits. | today~2, week~2, list-states~2, edit-states~2, archived-list, list-states.all-archived, edit-states.archived. |
| Auth | None. | "Nobody signs in". |
| Integrations | None. | The app is private and works offline; nothing is shared. |
| Look | Every style comes from `src/theme/tokens.ts`: light and dark palettes, plus 8 habit colours per scheme (Violet, Green, Amber, Red, Teal, Pink, Blue, Grey, in index order with Violet = 0). `use-palette.ts` resolves "system" against `useColorScheme`. `pnpm lint` (`scripts/tokens-only.mjs`) blocks raw values. On the web the `<html>` element gets `data-theme` and `color-scheme`. Archived rows in Settings reuse the habit colour swatch and the Today row's "Best: <n>" text. | theme: "System", "Light" and "Dark", applied at once. The glossary's 8 colours with Violet the default; light and dark themes. archived-list.shows: "'Stretch' in Teal, 'Best: 4'". |
| Tests | Jest (`jest-expo`) runs `src/**/*.test.ts(x)` for the `utest` items (store, days, streaks), against a `node:sqlite` Db swapped in by `useDbForTests`. Playwright runs `e2e/` at 375×812 with touch for the `e2e` items, against the `dist-e2e` web export built with `EXPO_PUBLIC_AIOS_TEST_HOOKS=1`. The test hooks (`src/lib/test-hooks.ts`) are the `/__test/reset`, `/__test/seed?name=` and `/__test/force?route=&mode=empty\|slow\|error` routes; `faults.ts` makes writes or reads fail. A `SeedHabit` gains `archivedAgo` (days ago) and `restorePlace`, and each archived state the items name gets a seed. `force?route=settings/archived` drives the archived section's states. JUnit output goes to `reports/`. | Each Done-when item's `Needs:`. archive.*, restore.* and list-states.archived-error need habits that are already archived, archived on a given day, or whose archived list fails to read. |
| Days | `src/lib/days.ts` keeps days as local `YYYY-MM-DD` strings. `canTick` checks a day against `lastSeven(today())` when the save runs. `use-today.ts` moves the date at local midnight, on returning to the foreground or tab focus, and on a 5 s poll. Archived days aren't stored as anything. Once the habit is restored, they're ordinary unticked days, tickable while inside the window. | tick-window, no-old-ticks, day-rollover (midnight within 10 s), "Day boundaries follow the phone's local midnight", and restore.tick-archived-days. |
| Streaks | `src/lib/streaks.ts` works out `current` (ending today if today is ticked, otherwise yesterday) and `best` (the longest run) from the ticked dates on every render. They're never stored. Days spent archived have no ticks, so they break the run without any extra code. | streaks: "worked out from the ticks each time and never stored". restore.streak: "0-day streak" and "Best: 3". |
| Saving | Every change is one transaction over what it touches. `deleteHabit` and `deleteAll` remove ticks and habits together, archived ones included. `toggleTick` reads and writes in one transaction. `toggleTick` and `setTick` refuse inside that transaction, with nothing stored, when the habit is archived (`archived_at IS NOT NULL`). They also refuse when `kv.failedTick` holds another change whose day is still tickable and whose habit exists and isn't archived; the retry of that change is allowed. `src/lib/use-save.ts` queues changes in order, so none is dropped, and shows "Couldn't save your change" with a "Try again" that reruns the same change. When a tick fails, `use-save` bumps a generation counter, and tick changes queued before the failure are refused without running; their boxes keep showing the stored state. A failed tick goes into `kv.failedTick` as `{habitId, day, ticked}`. The retry runs `setTick` with that intended state and day, and a retry refused by the window clears it. | save-error, failed-tick-kept~2 ("changes already waiting to save are refused"), no-lost-tick, no-partial-delete, no-archived-ticks, archive.clears-failed, delete-all.archived. |
| Reorder | `src/components/reorder-list.tsx` uses PanResponder with a 500 ms hold and an 8 px slop to pick a row up and drag it. The new order is saved with `reorder(ids)` into `position` (non-archived ids only), and the list changes only once the saved order comes back. Screen readers get "Move up" and "Move down" accessibility actions. A long press on the name doesn't open Edit. | reorder: the 500 ms long-press and drag, the screen-reader actions, and the long press that doesn't open Edit. |
